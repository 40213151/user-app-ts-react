  3. 同期処理は冪等にする

  冪等とは、同じ処理が2回走っても結果が変わらないようにすることです。

  SaaS連携では、Webhookが再送されたり、自分たちのジョブがリトライされたりします。そのたびに毎回 create してしまうと、同じGoogle Chatメッセージからチケットが2つできたり、同じNotionページが重複登録されたりします。

  このプロジェクトでは、Google Chatなら message_name、LINE WORKSなら message_id、Google Drive/NotionならファイルIDやページIDのような「SaaS側の一意なID」を external_id として持ちます。なので、初回は作成、2回目以降は既存データを見つけて更新、という
  動きにできます。

  面接ではこう言えます。

  > 外部SaaSは再送やリトライが前提なので、処理を冪等にしました。SaaS側の一意なIDを内部のキーとして使い、同じイベントや同じドキュメントが何度来ても二重作成されないようにしました。

  4. 長時間同期はロック・再開・削除検知まで見る

  Google DriveやNotionの同期は、対象が多いと長時間かかります。長い処理では、途中で失敗する、同時に別の同期が始まる、ユーザーが同期対象を削除する、トークンが切れる、という問題が起きます。

  そこで KnowledgeRepositorySyncService では、同期中であることをロックして、同時実行を防ぎます。失敗したら失敗回数や次回スケジュールを保存します。さらに、同期対象が削除中なら途中で中断します。

  Notion同期では each_with_resumable_document_sync によって、すでに処理済みのページをスキップできます。つまり、途中で失敗して再実行しても、最初から全部やり直さずに済みます。

  面接ではこう言えます。

  > 大量データ同期は一発で必ず終わる前提にしませんでした。同時実行ロック、失敗時の再スケジュール、途中再開、削除中断を入れて、運用中に壊れにくい同期処理にしました。

  5. チャットSaaSごとの差分を内部モデルで吸収する

  Google ChatとLINE WORKSは、似たチャットツールでも概念が違います。

  Google Chatにはスペース、スレッド、メッセージがあります。なので、同じスレッド内のメッセージは同じチケットに紐付けられます。一方でLINE WORKSは、この実装では会話の区切りを取りにくいため、1問1答に寄せています。

  ただし、後続のチケット処理が毎回「これはGoogle Chatか？LINE WORKSか？」と意識すると、コードが複雑になります。そこで Helpdesk::Channel::*::Message のようなアダプタで、どのSaaSでも content, received_at, destination, related_ticket の形に揃えていま
  す。

  面接ではこう言えます。

  > SaaSごとの違いをチケット処理全体に漏らさず、チャネルアダプタ層で吸収しました。Google Chatはスレッド、LINE WORKSは会話IDやユーザーIDというように、各SaaSの都合はアダプタ内に閉じ込め、内部では共通のメッセージとして扱えるようにしました。

  6. Webhookは認証・即時ACK・非同期処理を分ける

  Webhookは、SaaS側から自社サービスへ飛んでくるリクエストです。ここで重要なのは、まず本当にSaaSから来たリクエストか検証することです。

  Google ChatではJWT検証、LINE WORKSでは署名検証をしています。これをしないと、第三者が偽の問い合わせイベントを送れてしまいます。

  また、Webhookの中でAI回答生成や外部API呼び出しなど重い処理を全部やると、SaaS側がタイムアウトして再送してくる可能性があります。なので、受信時は検証、保存、ジョブ投入までにして、重い処理は非同期Jobで行うのが安全です。

  面接ではこう言えます。

  > Webhookでは、まず署名やJWTで正当性を検証し、イベントを保存してから非同期Jobに流しました。SaaS側のタイムアウトや再送を考慮して、エンドポイントでは重い処理を抱え込まない設計にしました。

  7. 権限・ユーザー照合をSaaSの安定IDで行う

  チャット上の操作では、「回答にフィードバックできるのは質問した本人だけ」のような制御が必要です。

  このとき、表示名で判定すると危険です。表示名は変えられますし、同姓同名もあります。メールアドレスも設定や権限によって取れない場合があります。

  そこで、Google Chatなら sender_name や user_name、LINE WORKSなら userId のような、SaaSが提供する安定した識別子で照合します。

  面接ではこう言えます。

  > 権限判定には表示名ではなく、SaaSが保証する安定IDを使いました。チャット連携ではユーザー名や表示名は信頼せず、Google Chatのリソース名やLINE WORKSのuserIdで本人確認するようにしました。

  8. SaaS固有形式を検索可能な共通形式に正規化する

  Google DriveやNotionのデータは、そのままだと形式がバラバラです。

  Google Docs、Spreadsheet、Slides、PDF、Notionページなど、それぞれ取得方法も中身の構造も違います。でもAIヘルプデスクや検索/RAGで使うには、最終的に「タイトル」「本文」「URL」「バージョン」「外部ID」のような共通の形にしておく必要があります。

  このプロジェクトでは、Google Docs系はOffice形式にexportし、NotionはMarkdown化して KnowledgeDocument に保存しています。こうすると、後続の検索・差分検知・参照表示がSaaSごとに分岐しなくて済みます。

  面接ではこう言えます。

  > SaaSごとのデータ形式をそのまま内部に持ち込まず、検索やRAGで扱いやすい共通ドキュメント形式に正規化しました。外部ID、URL、バージョン、本文を揃えることで、Google DriveでもNotionでも後続処理を共通化できます。
