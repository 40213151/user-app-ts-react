  1. GraphQL の N+1 解消
  PR: #987 フィードバック詳細上の機能をチケット詳細に移動する 

  チケットの latestFeedback 取得で、チケットごとに最新フィードバックを取りに行く実装を GraphQL::Batch::Loader に変更しています。
  TicketFeedbackPolicy::Scope による権限チェックを維持しつつ、複数チケット分をまとめて取得する形にして、テストでも SQL 数が <= 3 で
  あることを検証しています。

  面接ではこう言えます。

  > チケット詳細に最新フィードバックを表示する機能を追加した際、単純に各チケットから ticket_feedbacks.order(...).first を呼ぶと
  > GraphQL で N+1 が起きることに気づきました。そこで GraphQL::Batch::Loader を使い、表示対象チケットの ID をまとめて取得し、
  > TicketFeedbackPolicy::Scope の権限チェックを通したうえで最新フィードバックを一括取得するようにしました。テストでも SQL 発行数が
  > 増えないことを確認し、機能追加と同時に一覧・詳細表示のスケール性を担保しました。

  2. 大量ファイルアップロードの安定化・負荷分散
 

  ナレッジドキュメントのアップロードで、CloudFront/S3 への直接アップロード、3並列アップロード、GraphQL mutation の5件ずつチャンク分
  割を入れています。
  大量ファイルを1回の巨大 mutation / 1トランザクションで処理するリスクを避け、50ファイル上限も残してガードレールを置いています。

  面接ではこう言えます。

  > ナレッジドキュメントのアップロードで、ファイル数制限を緩和するにあたり、単に上限を外すと Rails・GraphQL・DB トランザクションに負
  > 荷が集中する問題がありました。そこでファイル本体は CloudFront 経由で S3 に直接アップロードし、フロント側では3並列に制御しまし
  > た。その後、メタデータ登録の GraphQL mutation は5件ずつチャンク分割し、部分失敗も扱えるようにしました。ユーザー体験を改善しつ
  > つ、バックエンドに巨大リクエストを投げない設計にした点が工夫です。

  3. チャット連携の検索・外部通信コスト削減


  LINE WORKS では user_id を保存し、company_id, conversation_id, user_id の複合インデックスを追加してフィードバック検索範囲を絞って
  います。
  Google Chat では company_id, space_name, thread_name の複合インデックス追加と、Webhook JWT 検証用の Google 証明書を1時間キャッシュ
  する実装が入っています。

  面接ではこう言えます。

  > チャット連携では、メッセージ量が増える前提で検索条件とインデックス設計を意識しました。LINE WORKS では会話 ID とユーザー ID で対
  > 象メッセージを絞れるようにカラムと複合インデックスを追加し、フィードバックコメントの検索範囲を小さくしました。Google Chat では本
  > 番のスレッド検索パターンに合わせて複合インデックスを追加し、Webhook 検証で使う Google 証明書も毎回外部取得せず1時間キャッシュし
  > ました。機能実装だけでなく、運用時の検索コストや外部 API 待ちも減らすことを意識しました。

  まで話せるので面接向きです。実測 ms の数字はPR上では見つからなかったので、そこは盛らずに「SQL数」「3並列」「5件チャンク」「1時間
  キャッシュ」のような実装上の具体値で話すのが安全です。
